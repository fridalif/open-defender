# Агент open-defender: справочник сообщений

Что отправляет агент (`open-defender/pkg/connector`) и что он ожидает получить в ответ.

Транспорт: одно WebSocket-соединение с `exporter.endpoint_address`. Каждый фрейм - это JSON-конверт `Envelope`, зашифрованный оконечным шифрованием (RSA-OAEP/SHA-256 для ключа AES, AES-256-GCM для тела, структура фрейма: `[RSA(aes_key)][12-byte nonce][ciphertext]`).

---

## 1. Ключи и идентификация

| | |
|---|---|
| Пара ключей агента | RSA-2048, создаётся в `connect()` **для каждого сеанса**, никогда не сохраняется |
| Ключ сервера | `exporter.endpoint_rsa_public_key`, base64 PKCS#1, из загруженного `config.yaml` |
| Идентификация | `exporter.user_id` + `exporter.config_id`, передаются в каждом конверте |
| Агент → сервер | шифруется ключом сервера |
| Сервер → агент | шифруется публичным ключом сеанса, переданным в `system/hello` |

Поскольку пара ключей создаётся для каждого сеанса, после переподключения все сообщения предыдущего сеанса невозможно расшифровать; на диске нет долговременного секрета агента.

> Агент **не аутентифицируется**: `user_id` и `config_id` - идентификаторы, а не секреты. Любой, у кого есть копия `config.yaml`, может выдать себя за этого агента. См. TODO.md, «Аутентификация агента».

## 2. Обмен сообщениями

```text
        агент                                     сервер (панель)
          |                                              |
          |  WebSocket dial: exporter.endpoint_address   |
          |--------------------------------------------->|
          |                                              |
  ключ RSA |  system/hello            task_id 0           |
  сеанса   |  payload.public_key = публичный ключ сеанса  |
  создан   |--------------------------------------------->|
          |                                              |
          |           config/set_config   task_id N      |  должен прийти
          |<---------------------------------------------|  в течение 30 с
          |  system/ack   task_id N   status ok | error  |
          |--------------------------------------------->|
          |                                              |
  ====================== сеанс установлен ======================
          |                                              |
          |  alert/raised   task_id 0   одно событие     |  без ack,
          |--------------------------------------------->|  без повтора
          |                                              |
          |           config/get_config   task_id M      |
          |<---------------------------------------------|
          |  config/config   task_id M                   |
          |--------------------------------------------->|
          |                                              |
          |           config/set_config   task_id K      |
          |<---------------------------------------------|
          |  system/ack   task_id K                      |
          |--------------------------------------------->|
          |  конфигурация отличается -> записать config.yaml,
          |  перезапустить, новый сеанс, новая пара ключей
          |                                              |
          |           ping   каждые 30 с                 |
          |<---------------------------------------------|
          |  pong                                        |
          |--------------------------------------------->|
          |                                              |
```

Всё выше двойной линии - фиксированное рукопожатие: `hello`, затем `set_config`, затем `ack`. Ниже линии порядок произвольный: агент отправляет предупреждения, как только монитор их создаёт, и отвечает на всё, что присылает сервер. Все фреймы в обоих направлениях являются зашифрованными конвертами; используемый ключ зависит только от направления (см. раздел 1).

## 3. Отправляется агентом

### 3.1 `system/hello`: открывает сеанс

```json
{
  "version": 2,
  "task_id": 0,
  "service": "system",
  "operation": "hello",
  "configuration_id": "<exporter.config_id>",
  "user_id": "<exporter.user_id>",
  "payload": {
    "public_key": "<base64 PKCS#1 публичного ключа сеанса>",
    "agent_version": "v1.3.0"
  }
}
```

**Ожидает:** `config/set_config` в течение 30 с. Любое другое сообщение прерывает сеанс.

### 3.2 `system/ack`: результат задачи

```json
{
  "version": 2,
  "task_id": 42,
  "service": "system",
  "operation": "ack",
  "configuration_id": "...",
  "user_id": "...",
  "payload": { "status": "ok", "error": "" }
}
```

`status` имеет значение `error` с заполненным `error`, когда конфигурацию не удалось разобрать, она не прошла проверку или не может быть записана на диск. `task_id` повторяет идентификатор запроса; для рукопожатия он равен `0`.

**Ожидает:** ничего.

### 3.3 `config/config`: ответ на `get_config`

```json
{
  "version": 2,
  "task_id": 42,
  "service": "config",
  "operation": "config",
  "configuration_id": "...",
  "user_id": "...",
  "payload": { "config": { "ssh_monitor": { "mode": "logger", ... }, ... } }
}
```

Тело - это работающий `config.yaml`, сериализованный в JSON. Ключи JSON совпадают с ключами YAML (`pkg/config/model.go` содержит теги и `yaml`, и `json`), что и делает возможным обмен в обоих направлениях.

**Ожидает:** ничего.

### 3.4 `alert/raised`: событие безопасности

```json
{
  "version": 2,
  "task_id": 0,
  "service": "alert",
  "operation": "raised",
  "configuration_id": "...",
  "user_id": "...",
  "payload": {
    "events": [
      {
        "source": "ssh_monitor",
        "ip": "203.0.113.7",
        "message": "ssh_monitor -> found offenders ip 203.0.113.7 while scanning syslog: /var/log/auth.log-sshd",
        "happened_at": "2026-07-24T10:15:00Z",
        "details": { "engine": "syslog", "source": "/var/log/auth.log" }
      }
    ]
  }
}
```

Один конверт содержит одно событие. **Ожидает:** ничего: доставка выполняется не более одного раза, подтверждений и повторной отправки нет.

#### Источники событий

| `source` | Возникает, когда | Дополнительные поля |
|---|---|---|
| `ssh_monitor` | `tries` неудачных входов SSH с одного IP за `window_seconds` | `details.engine`, `details.source` |
| `web_brute_monitor` | то же для страниц входа веб-сервера | то же |
| `web_recon_monitor` | то же для запросов несуществующих путей | то же |
| `database_monitor` | то же для неудачных входов в базу данных | то же |
| `network_antirecon` | eBPF обнаруживает сканирование портов или обращение к порту из чёрного списка | нет |
| `resource_monitor` | CPU / RAM / трафик / диск превысили предел | `severity` (`warning` или `alert`), `details.metric`, `details.value`, `details.unit`, `details.limit` |
| `ip_ban` | IP действительно заблокирован межсетевым экраном | нет |

`severity` устанавливается только для `resource_monitor`. Уровни важности для панели назначаются коннектором, а не агентом.

## 4. Принимается агентом

### 4.1 `config/set_config`

```json
{
  "version": 2,
  "task_id": 42,
  "service": "config",
  "operation": "set_config",
  "payload": { "config": { ... } }
}
```

Обработка по порядку:

1. Декодировать в основу `config.New()`, чтобы ключи, отсутствующие в полезной нагрузке, сохраняли собственные значения агента по умолчанию, а не становились нулевыми значениями.
2. **Заменить `exporter` локальным значением.** Панель хранит раздел exporter пустым до загрузки `config.yaml`; дословное применение удалило бы адрес конечной точки и ключ, оставив агента без связи.
3. **Объединить `ip_whitelist` с адресами самой машины.** Конфигурация панели начинается с пустого белого списка; дословное применение позволило бы монитору в режиме blocker заблокировать сам хост.
4. `Validate()`. При ошибке ничего не записывается, а ack содержит `status: "error"`.
5. Сравнить с работающей конфигурацией. Если они равны, отправить ack `ok` и больше ничего не делать. Это предотвращает перезапуск агента при каждом переподключении во время рукопожатия.
6. Иначе записать `config.yaml`, отправить ack и запросить перезапуск.

**Отвечает:** `system/ack`.

### 4.2 `config/get_config`

```json
{
  "version": 2,
  "task_id": 42,
  "service": "config",
  "operation": "get_config",
  "payload": {}
}
```

**Отвечает:** `config/config` с работающей конфигурацией.

### 4.3 Всё остальное

Записывается в журнал и игнорируется; сеанс остаётся открытым.

## 5. Перезапуск при новой конфигурации

Конфигурация, пришедшая **с сервера** и действительно отличающаяся от работающей, перезапускает мониторы через контекст:

```text
connector.applyConfig()      записывает config.yaml
connector.requestRestart()   сигнализирует monitorHub.restart, затем cancel()
        |
        v
контекст отменён -> все мониторы, программа eBPF и сам коннектор останавливаются
        |
monitorHub.runCycle() завершает работу, wg.Wait() освободился
        |
monitorHub.RunMonitoring() видит сигнал перезапуска
        |  перечитывает config.yaml с диска
        |  создаёт новый ctx/cancel и WaitGroup
        v
runCycle() запускает все мониторы и новый сеанс коннектора
```

Коннектор никогда не записывает общий `*config.Config` самостоятельно; он записывает только файл. Перезагрузка происходит в `RunMonitoring` после остановки всех мониторов, поэтому никто не читает структуру во время её замены.

Перезапуск означает новый сеанс: новую пару ключей RSA и новый `system/hello`.

## 6. Тайминги и ограничения

| | Значение | Примечания |
|---|---|---|
| Тайм-аут соединения | 15 с | |
| Бюджет чтения рукопожатия | 30 с | на сообщение |
| Крайний срок чтения | 90 с | обновляется каждым ping сервера |
| Крайний срок записи | 15 с | |
| Максимальный размер фрейма | 1 МБ | `SetReadLimit` |
| Задержка переподключения | 5 с, +10 с за каждую неудачу, максимум 100 с | сбрасывается после успешного подключения |
| Очередь экспорта | 1024 конверта | при заполнении события отбрасываются, мониторы никогда не блокируются |

Сервер отправляет ping каждые 30 с и отключает сеанс, если не получает pong в течение 75 с. Агент отвечает на ping из обработчика ping, поэтому для сохранения сеанса `readLoop` должен продолжать работу.

## 7. Поведение при сбоях

| Ситуация | Действие агента |
|---|---|
| Конечная точка недоступна | бесконечно повторяет попытки с увеличивающейся задержкой |
| Некорректный `endpoint_rsa_public_key` | пишет в журнал и повторяет попытки; не подключается, пока конфигурация не будет исправлена |
| Рукопожатие возвращает не `set_config` | закрывает соединение и повторяет попытку |
| Конфигурация в полезной нагрузке недействительна | подтверждает с `status: "error"`, продолжает работать со старой конфигурацией |
| Сервер закрывает соединение | `serve()` завершается, сеанс перезапускается из `connect()` |
| Канал отправки закрыт | отменяет корневой контекст и останавливает агента |
| `exporter.enabled: false` | коннектор никогда не запускается, события не ставятся в очередь |
